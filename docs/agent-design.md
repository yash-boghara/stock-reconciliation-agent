# Agent design decisions

Why the agent layer is built the way it is, including the alternatives that
were considered and rejected. Every number quoted here is regenerated by
`python3 -m src.recon.eval_report` — see [evaluation.md](evaluation.md).

---

## Where the model sits

```
  six messy CSVs
        │
        ▼
   ingestion ─────────────► quarantine (unparseable rows)
        │
        ▼
  150 reconciliation cases
        │
        ▼
   rules layer ──── 77% resolved, 100% precision ──┐
        │                                          │
        ▼ 23% residue                               │
   agent layer ──── 84% (ceiling 89.5%) ───────────┤
        │                                          │
        ▼                                          ▼
                    corrections
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
      auto            review          escalate
   (nobody)      (owning desk)   (loss prevention)
```

The model is deliberately the smallest box. Everything with a structural
signature is resolved before it, and everything it decides is routed to a
human after it. That is the design position, and it is why the agent never
sees 77% of the work.

---

## Decisions

### Why the agent only chooses among four causes

The tool schema constrains `cause` to an enum of the four judgement causes,
excluding the four the rules layer resolves. Offering all eight would invite
the model to re-litigate arithmetic that has already been proved exactly, and
any disagreement it produced would be a regression rather than a finding.

Narrowing the decision also narrows the failure. When the observed
contamination arrived, the `cause` field was untouched because it is
enum-constrained; only the free prose absorbed it. **Constrain the field that
drives the decision; treat everything else as advisory.**

### Why a manual loop rather than the SDK tool runner

The tool runner is the right default for most agents and would be less code.
It was rejected here for three specific reasons:

1. **Tool results are served, not executed.** Every tool reads local pipeline
   state. There is no I/O to orchestrate, which removes most of the runner's
   value.
2. **The evaluation needs the loop's internals.** Tool-call counts, per-case
   token usage, attempt counts and cache read share are all reported, and
   they come from inside the loop.
3. **The control has to substitute for the client.** The heuristic control
   runs through the same call path, which is what lets CI exercise the
   harness with no key. That is easier against a loop we own.

The loop is about forty lines. Owning it costs less than bending a helper
around those three constraints.

### Why these three tools, and no more

Each was ablated through the control itself — not a reimplementation, which
would have measured the copy:

| Evidence available | Residue accuracy |
|---|---|
| Nothing (majority class) | 41.4% |
| `get_sku_profile` | 73.1% |
| `+ get_sku_history` | 76.0% |
| `+ get_staff_notes` | 84.1% |

`get_sku_history` adds only ~3 points, which looks marginal until you ask
what it adds them *on*: it is the only evidence distinguishing a recurring
loss from a one-off, and that distinction is the entire shrinkage signal.
Dropping it would not cost much accuracy and would cost the ability to
identify theft at all.

A fourth tool was considered and rejected: supplier-level history. It would
help `short_delivery`, but that cause is bounded by GRN coverage rather than
by evidence the agent lacks, so the tool would spend context to move a
number that is capped elsewhere.

### Why the tools return pipeline output only

Every tool reads the catalogue, the assembled cases, or the rules layer's
findings. None reads `labels.csv`. A test enforces this by making the labels
file unreadable and running the whole layer, because a leak here would make
every downstream figure meaningless while making them all look better —
the failure mode that is hardest to notice and most fatal to trust.

### Why the control is not a mock

`HeuristicClient` answers the same tool calls against the same evidence with
no model at all. It serves three purposes at once: the offline test double,
the bar the model has to clear, and the ablation vehicle. If it were a mock
it would prove the harness runs; being a real classifier, it proves whether
the model is worth paying for.

It currently scores 84.1% against an 89.5% ceiling.

### Why prompt caching, and where the breakpoint goes

The system prompt and tool definitions are identical for every case in a run
and render before the per-case brief, so one `cache_control` breakpoint on
the last system block covers both. Measured on a real run, 74% of input
tokens were served from cache.

### Why structured outputs rather than parsing prose

`output_config.format` constrains the response to a JSON schema, so `cause`
cannot be a value the system does not understand and `confidence` cannot be
a synonym. The alternative — asking for JSON in the prompt and parsing it —
fails open: a malformed response becomes a guess. Here it raises.

### Why retries are selective

Rate limits, timeouts, connection failures and 5xx retry with exponential
backoff. A rejected key, a malformed request, or an exhausted balance does
not, because the second attempt fails identically and, on a paid path, costs
money to learn nothing. Backoff is exponential because the common transient
failure is a rate limit, and retrying one immediately is how a client turns
a single 429 into several.

### Why confidence does not auto-post, even though it is calibrated

The stated confidence predicts correctness cleanly — 99.5% / 84.9% / 48.0%
across 100 seeds — so it is a usable signal rather than decoration. Routing
on it is therefore tempting, and measurable: auto-posting high-confidence
judgement calls under the value threshold would move **40% of the review
queue** to unattended, at the cost of a wrong posting in **0.76%** of them,
about one every seven runs.

It is off by default anyway. The gap between the rules layer (100% over
3,891 commitments) and a high-confidence judgement (99.5%) is the gap
between *proved* and *usually right*, and a system that posts to a ledger
without a human should sit on the proved side of it. `AUTO_POST_HIGH_CONFIDENCE`
exists as a lever with those numbers attached, rather than as a decision
buried in a routing function.

### Why `effort: medium`

The residue task is a bounded four-way judgement over retrieved evidence,
not open-ended reasoning. `medium` was chosen for that shape and is
configurable per run. It has **not** been swept — doing so needs an API key
and a few dollars, and quoting an unswept default as if it were tuned would
be exactly the kind of unmeasured claim the rest of this project avoids.

## What it costs

Measured on a real contested-case run — 9 cases, 10,178 input tokens,
29,002 served from cache, 2,694 output — at published Claude Opus 5 rates:

| | |
|---|---|
| Cost per case | **$0.0147** |
| Full 35-case residue run | **$0.52** |
| Input served from cache | **74%** |

The 100-seed evaluation costs nothing, because it runs the control.

The economics are the argument for the architecture. Rules resolve 77% of
cases at no per-case cost, so the model is only ever asked about the 23% that
need judgement — and of that 23%, only the ~24% carrying an oblique note can
possibly benefit. Paying a model for the rest buys a re-derivation of the
control's answer.

## What is not built, and why

- **A model-vs-control result at scale.** Nine contested cases cannot resolve
  a five-point effect; the harness reports McNemar precisely so that a tie is
  read as "no evidence" rather than "no difference". Settling it needs a few
  hundred contested cases.
- **Retrieval over resolved historical cases.** The decision log now exists
  to retrieve from; the tool over it does not. It needs a corpus of real
  reviewer decisions to be worth anything, which is a deployment away.
- **Fine-tuning.** There is no training set worth the name, and the ceiling
  analysis says the remaining headroom is in reading free text — which a
  general model already does well.
